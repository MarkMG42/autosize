# Возможность размещать размеры в свободном пространстве

Статус: исследование API; **алгоритм свободных областей не реализован**.
Исследование выполнено по просьбе пользователя отдельно от масштабирования
рабочих размеров на все тела рамы.

## Вывод

Это реализуемо как отдельный алгоритм компоновки. Успешная нативная проба уже
подтвердила, что истинный размер трубы 1500 мм можно привязать к реальному ребру,
переместить в заданную XY-точку через калибровку и сохранить привязку после
возврата режима касательных кромок. Но достижимость точки не доказывает, что
эта точка свободна от геометрии или что выносные линии проходят удачно.

Для первого варианта разумно искать внешние коридоры слева, справа, сверху
и снизу от проекции сборки. Это проще и надёжнее, чем сразу использовать все
небольшие внутренние пустоты между элементами рамы. Возможность выбрать между
внешними коридорами и внутренними пустотами относится к будущей реализации.

## Что можно получить из API

Имена и сигнатуры ниже проверены по метаданным SolidWorks Interop 32.1.0 (API
2024); фактическая упаковка массивов и пространства координат ещё требуют
короткой нативной проверки в SolidWorks 2025.

| Данные / операция | API |
| --- | --- |
| Прямоугольник вида | `IView.GetOutline` |
| Отображаемая геометрия | `IView.GetDisplayData4`, `GetPolylines7(CrossHatchOption, ByRef Polylines)` |
| Примитивы отображения | `IDisplayData.GetLineCount/GetLineAtIndex3`, `GetArcCount/GetArcAtIndex2`, `GetPolyLineCount/GetPolylineAtIndex2`, `GetPolygonCount/GetPolygonAtIndex` |
| Отображаемое оформление аннотации | `IAnnotation.GetDisplayData` |
| Текст | `IDisplayData.GetTextCount`, `GetTextAtIndex`, `GetTextPositionAtIndex`, `GetTextHeightAtIndex`, `GetTextFontAtIndex`, `GetTextAngleAtIndex`, `GetTextPlaneAtIndex` |
| Виды листа | `IDrawingDoc.GetFirstView`, `IView.GetNextView`, `ISheet.GetViews` |
| Аннотации и таблицы | `IView.GetAnnotations`, `GetTableAnnotations` |
| Формат листа | `ISheet.GetTemplateSketch`, `ISketch.GetSketchSegments` |
| Габариты заметки | `INote.GetExtent` |
| Автоматическое упорядочивание | `IModelDocExtension.AlignDimensions(AlignType, SpaceValue)` |

`GetOutline` — только грубый прямоугольник. Он не показывает свободные отверстия
между профилями и не заменяет карту препятствий.

`AlignDimensions` имеет режимы AutoArrange, SpaceEvenly, Colinear, Stagger и
выравнивание текста. Интерфейс не принимает пользовательскую карту препятствий;
считать его гарантированным поиском свободного пространства нельзя. Проверка
истинного значения, позиции и привязок нужна и после автоматического выравнивания.

## Предлагаемый будущий алгоритм

1. Построить карту занятой области **всей проекции сборки**, включая проушины,
   уголки, ножки и прочие аксессуары. Ограничение «только тела рамы» применяется
   к создаваемым размерам, но не к препятствиям.
2. Для первого варианта использовать консервативные заполненные проекции тел:
   проекции углов их bounding box → выпуклые оболочки с запасом. Для этого нужны
   правильная конфигурация экземпляра и преобразование в текущий вид. Нельзя
   без проверки брать геометрию другой активной конфигурации через GetModelDoc2.
   Затем уточнять данные полилиниями и силуэтами фактически отображаемого вида.
3. Не считать область внутри сплошной грани пустой только потому, что в ней нет
   линий. Карта одних рёбер недостаточна: нужны заполненные области или консервативные
   оболочки. Внутренние отверстия уточнять отдельно после проверки их представления.
4. Резервировать другие виды вместе с их аннотациями, рамку листа, основную
   надпись, таблицы, заметки и существующие размеры. Одного целевого вида мало.
5. Искать коридоры нужного размера с запасом, ранжируя их по расстоянию до своего
   тела и числу пересечений размерных/выносных линий с посторонней геометрией.
   Запрещать любое касание выносной линии с исходным телом нельзя — она должна
   начинаться у измеряемой геометрии.
6. После реального переноса проверять оформление, физическую длину, положение,
   отсутствие dangling и пересечения. Целевой XY-коридор ещё не гарантирует
   корректную трассировку всех размерных линий в изометрии.

## Точные габариты текста

В исследованном интерфейсе нет общего `IAnnotation.GetBox`. У DisplayData
найдены позиция, высота, угол и шрифт, но не универсальная ширина глифов.
`GetTextInBoxWidth/HeightAtIndex` относятся к тексту в рамке; `INote.GetExtent`
нельзя автоматически применять к размерным аннотациям.

Возможный путь — измерять фактически отображаемую строку средствами Windows
с нужным шрифтом и запасом, затем проверять в нативном отображении. Допуски,
дроби, специальные символы, повёрнутые строки и составные надписи требуют
отдельных примеров. До такой проверки следует сохранять консервативные области,
а не обещать точное отсутствие пересечений.

## Ограничения текущего механизма перемещения

Калибровка истинных изометрических размеров уже проверена на одиночных размерах,
но текущий код ограничивает обратную поправку команды величиной 50 мм и использует
локальную модель отклика. Для выноса далеко за проекцию этот предел и стратегию
шагов нужно исследовать заново, сохранив проверки истинного значения и привязок.
Простое увеличение предела без проверки не является реализацией компоновки.

## Минимальная следующая проверка — только после решения внедрять

Вид рамы с аксессуарами, соседним видом и основной надписью:

1. Без перемещения размеров проверить, что карта препятствий покрывает реальную
   геометрию и не объявляет сплошные грани пустыми.
2. Вынести один размер в выбранный внешний коридор.
3. Сверить текст, размерную линию, выноски, истинное значение и отсутствие dangling.
4. После успешного примера расширять обработку на группу размеров.

В текущий массовый макрос этот алгоритм не добавлен: прежний поиск места рядом
с ребром сохранён. Исследование не является доказательством готовой автоматической
раскладки в пустом пространстве.
