# AutoDimensionFrame 2.4.3

Исправленная версия приложенного `AutoDimensionFrame (9).bas` (2.3).
Исходный файл не изменён. Это исходник VBA для SolidWorks 2025, а не готовый `.swp`.

## Запуск

1. На копии чертежа откройте VBA-проект макроса в SolidWorks.
2. Удалите из проекта старый модуль `AutoDimensionFrame` и импортируйте новый
   `AutoDimensionFrame.bas`. Сохраните исходный макрос отдельно.
3. Выполните Debug → Compile в редакторе VBA. Нужны стандартные ссылки
   SolidWorks type library и SolidWorks constants type library.
4. Откройте/разрешите исходные модели. Если API сообщает имя ссылочной
   конфигурации, оно должно совпадать с активной конфигурацией исходной модели.
   Пустое имя означает, что API его не сообщил; оно больше не считается
   несовпадением. Проверки соответствия рёбер и длины остаются обязательными.
   Макрос сам конфигурации не переключает.
5. Выберите рамку одного чертёжного вида и запустите `main`.
   Как в 2.3, тип размеров вида должен быть True, не Projected.
6. Проверьте результат и журнал VBA Immediate (Ctrl+G), особенно `UNRESOLVED`,
   `SOURCE MAPPING FAILED`, `Configuration mismatch` и `STOP`.
   Документ автоматически не сохраняется.

## Исправление 2.4.3

Журнал 2.4.2 показал девять отказов `Cannot uniquely resolve drawing component`,
`matches=0`, до обработки рёбер. Старый поиск требовал полного совпадения имени
компонента чертежа с именем в дереве сборки. Он не учитывал представление,
в котором чертёж добавляет имя своего корня перед относительным путём экземпляра.
Точный вид имён дерева модели в том журнале отсутствовал.

Новый поиск сравнивает исходное имя экземпляра с двумя представлениями:
`actual.Name2` и `drawingRoot + "/" + actual.Name2`. Имена корня берутся
из `View.RootDrawingComponent.Name` и его `Component.Name2`.
Имена реальных экземпляров не обрезаются. Все промежуточные подсборки и номера
экземпляров сохраняются; совпадения только по имени детали не допускаются.

Каждый реальный экземпляр считается один раз. Если точная и корневая формы
дали разные экземпляры, неоднозначность не скрывается. Проверки пути файла
и известной конфигурации сохраняются.

В начало журнала добавлены оба имени корня и первые восемь имён дерева модели.
Для поиска отдельно выводятся `name matches`, `path rejected`, `config rejected`,
`accepted`; при отклонении пути/конфигурации выводятся оба сравниваемых значения.
Это позволит установить причину, если представления имён отличаются иначе.

## Исправление 2.4.2

В переданном фрагменте журнала 2.4.1: `created=0`, `failed=0`, `bodies=51`,
`unresolved=51` и 149 сообщений `SOURCE MAPPING FAILED`. Отказ происходил до
вызова создания размеров: сравнивались сущности в разных контекстах.

Теперь компонент из чертежа разрешается в реальный экземпляр документа сборки
через `ModelDocExtension.GetCorresponding2`, с проверкой по дереву сборки.
Резервный поиск — уникальное полное имя экземпляра с учётом корня чертежа
и проверкой пути файла, а не имя детали без пути вложенности.

Видимое ребро переводится в контекст исходной детали методом
`sourceModel.Extension.GetCorrespondingEntity2`, после чего проверяется
принадлежность исходной геометрии. Равенство идентичности ребра детали и ребра
чертежа не требуется. Если обратный переход не удался, резервный маршрут:
исходная деталь → реальный экземпляр сборки → выбранный вид, с явным
`View.GetCorresponding` на последнем шаге. Проекция использует преобразование
того же реального экземпляра. Для детали сборочного преобразования нет.

Криволинейное ребро больше не блокирует постановку длины прямого ребра тела.
Несопоставленное **прямое** ребро по-прежнему блокирует тело: короткая сторона
профиля не подставляется вместо неизвестной максимальной длины.

В журнале отдельно показаны разрешённый экземпляр, число исходных рёбер,
успехи обратного/прямого сопоставления, возвраты `Nothing`, неожиданные типы,
чужая исходная геометрия и первые ошибки API каждого маршрута.

## Исправление 2.4.1

Журнал запуска 2.4 показал девять отказов до обхода тел: у всех компонентов
`ReferencedConfiguration` вернул пустое имя (`instance=`). Код ошибочно сравнивал
его с непустым именем активной конфигурации и объявлял несовпадение.
Теперь пустое имя журналируется как неизвестное и не блокирует обработку.
Проверка непустого несовпадающего имени, сопоставление рёбер, отказ тела при
неполном сопоставлении и проверка длины созданного размера сохранены.
Такая же обработка пустого имени применяется к виду отдельной детали.

## Изменения относительно 2.3

- Раздельная обработка вида детали и сборки.
- Видимое ребро переводится в контекст исходной детали через
  `ModelDocExtension.GetCorrespondingEntity2`. Резервный прямой маршрут использует
  `Component2.GetCorresponding`, `View.GetCorresponding` и `SldWorks.IsSame`.
  Координаты берутся у исходного ребра; преобразования экземпляра и вида
  применяются по одному разу.
  Выбор между двумя координатными маршрутами по попаданию в outline удалён.
- Рёбра с неизвестным соответствием не подменяются произвольно: тело остаётся
  `UNRESOLVED`. Сборочные вырезы могут создавать именно такие рёбра.
- Сохранено назначение исходника: одна длина самого длинного видимого прямого
  ребра на тело каждого экземпляра. Это не все размеры рамы и не длина заготовки
  по cut list. Если продольное ребро разбито/скрыто, нужна отдельная стратегия.
- Убрано исключение всех рёбер короче 20 мм. Параллельные лучу зрения рёбра
  с практически нулевой проекцией остаются неподходящими для расстановки.
- При отказе пробуются другие рёбра той же максимальной длины. Короткая сторона
  профиля не подставляется вместо длины тела.
- Надпись ищет место по обе стороны ребра на расстоянии 4–12 мм, с небольшим
  смещением вдоль него. Позиция ограничена исходным прямоугольником вида и листом.
  Произвольного переноса к центру вида/углу листа нет.
- После создания проверяются истинная длина, результат перемещения аннотации
  и фактически прочитанная позиция. Неподходящая новая аннотация удаляется;
  неопределённый результат создания/удаления останавливает макрос.
- Тела без размера и причины неудачных попыток выводятся в журнал.

## Ограничения

Габариты текста оценены по длине числа и высоте шрифта. Это не точный габарит
отрисованных символов, допусков, размерных и выносных линий. Проверяются
оценочные области текста и уже существующих размеров выбранного вида;
геометрия модели, заметки и размеры соседних видов как препятствия не анализируются.
При тесной раскладке размер останется `UNRESOLVED`, а не будет вынесен далеко.

Существующие размеры не удаляются и не исправляются. Повторный запуск может
создать дубликаты: для сравнения версий используйте чистую копию чертежа.
Не проверены специальные виды (разорванные, обрезанные, разнесённые и т.п.).
Недоступные/lightweight-модели нужно разрешить заранее. При разных конфигурациях
одной детали в сборке возможен явный отказ части компонентов.

## Что проверено

В облаке выполнен статический разбор и независимый review двумя агентами.
Проверены структура процедур, ограничения строк VBA и численные сценарии поиска
позиции. Компиляция VBA и выполнение в SolidWorks здесь недоступны.
Версии 2.4 и 2.4.1 запущены пользователем в SolidWorks: первая остановилась на
пустых именах конфигураций, вторая — на отсутствии сопоставления рёбер.
Версия 2.4.2 также проверена пользователем: девять отказов поиска экземпляра
в дереве сборки. Версия 2.4.3 ещё не проверена запуском в SolidWorks 2025.
Для 2.4.3 дополнительно пройдены 17 сценариев правил сопоставления имён:
выражения чистой VBA-функции извлечены из исходника и вычислены в Python.
Проверены корневые префиксы, вложенные одинаковые имена, коллизии и пустой корень.
Это проверка правил строкового сопоставления, не компиляция VBA и не COM-тест.

Существование и сигнатуры новых методов дополнительно проверены по метаданным
`SolidWorks.Interop.sldworks` 32.1.0 (NuGet, API 2024). Это проверка интерфейса,
не подтверждение выполнения переходов контекста на конкретном чертеже.
Временный анализатор метаданных и DLL не являются зависимостями макроса.
В новом журнале сначала проверьте ненулевые `reverse/local` или `forward`
и максимальные длины тел; затем — результаты создания и положение надписей.

Для native-проверки сравните отдельную деталь рамы с той же деталью в сборке,
включая смещённый, повёрнутый и вложенный экземпляры. Повторите на разных
масштабах вида. Проверьте длины, привязки, близость надписей и причины пропусков.
Для тесного вида убедитесь, что неудачная попытка удалена, существующие размеры
сохранены, а настройка Input dimension value восстановлена.
